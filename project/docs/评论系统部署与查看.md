# 评论系统部署与查看

评论页面已经包含在 Astro 的静态构建中。评论接口是 `dist/api/comments.php`，使用服务器现有的 PHP 和 MySQL。只上传静态文件、但没有给站点启用 PHP 时，评论无法工作。

## 在本地完整预览

`npm run dev` 仍适合修改静态页面，但它不会执行 PHP，评论区会提示加载失败。要测试真实评论收发，先运行 `npm run build`，准备一个本地 MySQL 数据库并导入 [`server/schema.sql`](../server/schema.sql)，再把 [`server/website-comments-config.example.php`](../server/website-comments-config.example.php) 复制成项目根目录的 `website-comments-config.php`，填入本地数据库信息。这个配置文件已被 Git 忽略。

安装了 PHP CLI 和 `pdo_mysql` 后，在项目根目录运行：

```bash
php -S 127.0.0.1:8088 -t dist server/dev-router.php
```

随后打开 `http://127.0.0.1:8088/notes/某篇笔记地址`。修改前端或 PHP 后重新运行 `npm run build`。本地调试产生的评论只存在本地数据库，不会出现在公网网站。

## 在宝塔服务器启用

1. 在宝塔的「数据库」中新建 MySQL 数据库 `website_comments` 和专用数据库用户。用管理员账户导入 [`server/schema.sql`](../server/schema.sql)。运行时用户只需要这个数据库的 `SELECT`、`INSERT`、`UPDATE`、`DELETE` 权限。
2. 复制配置样本为 `/www/wwwroot/website-comments-config.php`，填写数据库用户名和密码。`hash_key` 使用独立的随机长字符串，例如在服务器终端运行 `openssl rand -hex 32` 生成。正式站点把 `cookie_domain` 设为 `blueee.cn`，使 `blueee.cn` 与 `www.blueee.cn` 共用浏览器标识；本地预览时保持 `null`。不要把真正的配置文件上传到网站目录，也不要提交到 Git。PHP 运行账户必须能读取它。
3. 在宝塔「网站 → blueee.cn → PHP 版本」给站点启用 PHP 8.1 或更新版本，确认 `pdo_mysql` 扩展可用。站点根目录仍然是 `/www/wwwroot/website`。
4. 运行 `npm run build`，上传 `dist` **里面的内容**到站点根目录。确认其中有 `api/comments.php` 和 `generated/graph.json`。上传后用浏览器打开一篇笔记，提交一条测试评论并刷新，确认它仍在列表里。

如需修改配置文件位置，可设置 PHP-FPM 环境变量 `COMMENTS_CONFIG_PATH` 为它的绝对路径。默认位置是站点根目录的上一级目录，即 `/www/wwwroot/website-comments-config.php`。

如果访问 `/api/comments.php` 时浏览器显示或下载 PHP 源代码，说明站点尚未正确启用 PHP。先关闭评论入口，再修复宝塔的 PHP 配置。接口正常时会返回 JSON。

## 升级数据库以支持回复和访客昵称

回复（楼中楼）和访客自动昵称要求：`comments` 表带 `parent_id`（直接回复的评论）、`root_id`（所属楼层）、`author_key`（作者浏览器哈希）、`author_name`（昵称）四列，另有新表 `comment_identities` 记录昵称分配。在 2026-09-28 之前建好的数据库需要先迁移，否则接口会报错、评论拉不出来。

在宝塔「数据库 → phpMyAdmin → website_comments」的 SQL 页签执行 [`server/migrate-2026-09-28-comments.sql`](../server/migrate-2026-09-28-comments.sql) 的内容：

```sql
ALTER TABLE comments
    ADD COLUMN parent_id BIGINT UNSIGNED NULL AFTER note_slug,
    ADD COLUMN root_id BIGINT UNSIGNED NULL AFTER parent_id,
    ADD COLUMN author_key CHAR(64) CHARACTER SET ascii COLLATE ascii_bin NULL AFTER root_id,
    ADD COLUMN author_name VARCHAR(48) NULL AFTER author_key,
    ADD INDEX idx_comments_root (root_id, status, id);

CREATE TABLE IF NOT EXISTS comment_identities (
    author_key CHAR(64) CHARACTER SET ascii COLLATE ascii_bin NOT NULL PRIMARY KEY,
    display_name VARCHAR(48) NOT NULL,
    created_at DATETIME(6) NOT NULL,
    UNIQUE KEY uq_identities_name (display_name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

执行一次即可，重复执行会提示字段已存在，不影响数据。旧评论新增列都是 `NULL`，页面显示为「匿名」；新评论会自动带昵称。全新数据库直接导入最新的 `schema.sql`，无需这一步。

页面上每条评论带有 `#编号`，点「回复」后再发送即挂在对应楼层下；回复别人的回复时，会显示 `↩ 对方昵称`（找不到昵称时退回 `#编号`）便于跳回被回复的那条。回复同样受上面的限流和字数限制。

## 访客昵称规则

访客不需要填写任何信息：第一次成功评论时，系统按浏览器 Cookie 的哈希从词库里领一个「形容词 + 名词」的昵称（如 `稳健Biscuit`、`温柔海豚`、`BravePanda`，中英可混搭），永久绑定这个浏览器，之后每条评论都显示同一个名字和同色头像；全站昵称靠数据库唯一索引保证不重复，撞名时自动换下一个候选。输入框上方会提示「将以「xx」的身份发言」。

词库（形容词、名词各 48 个，中英各半）直接写在 `public/api/comments.php` 的 `name_bank()` 里，想增删词改那里即可，然后重新 `npm run build` 并上传。已分配的昵称存在 `comment_identities` 表里，改词库不影响老访客的名字。组合空间约 96 × 96 = 9216 个；因为查重兜底，用之前不会出现重名，真不够时扩词库或再加数字后缀都行。

固有限制：清掉 Cookie 或换设备/浏览器会领到新昵称，同一个人手机和电脑可能是两个名字。想给某位访客改名或清理昵称，在 phpMyAdmin 里改 `comment_identities.display_name`（注意保持唯一），同时把 `comments.author_name` 里对应评论一并更新。

## 规则与数据存放位置

成功发送评论时，浏览器会收到一个仅供评论接口使用的随机 `comment_visitor` Cookie；它设置为 `HttpOnly`、`SameSite=Lax`，在 HTTPS 下还会设置 `Secure`。删掉 Cookie 会重新开始该浏览器的计数，当前 IP 的计数仍保留。IP 仅从服务器连接的 `REMOTE_ADDR` 读取，不相信访客自己填写的转发请求头。如果将来加 CDN 或另一层反向代理，需要在可信代理层正确恢复访客 IP，否则所有读者可能被当作一个 IP。

| 对象 | 相邻两次成功评论 | 最近 5 分钟 | 最近 24 小时 |
| --- | --- | --- | --- |
| 同一浏览器 | 必须大于 5 秒 | 最多 10 条 | 最多 20 条 |
| 同一 IP | 必须大于 1 秒 | 最多 50 条 | 最多 200 条 |

每条评论最多 1000 字。超出额度返回 HTTP `429` 和 `Retry-After`，被拒绝的提交不会写入评论表或占用成功次数。评论只支持纯文本；前端按文本插入，不执行评论里的 HTML。

这些数值控制成功写入的评论。对于大量无效请求或不断触发 `429` 的请求，还需要在 Nginx 或 CDN 入口按 IP 限制 `/api/comments.php` 的 POST 请求频率，才能在请求到达 PHP 前拦截。可以参考 [Nginx 的 `limit_req` 文档](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)；宝塔生成的站点配置需要保留原有 PHP 处理规则。

在宝塔的「数据库 → phpMyAdmin → website_comments」可以查看四张表：

- `comments`：真实评论。`note_slug` 是笔记路径，`content` 是正文，`created_at` 是 UTC 时间，`status` 为 `visible` 或 `hidden`；`parent_id` 是直接回复的评论 id（顶层评论为 `NULL`），`root_id` 是所属楼层的顶层评论 id（回复挂在这条楼层下），`author_key` 是作者浏览器哈希（对外保密，用于识别同一访客），`author_name` 是评论时的昵称快照。将某条评论的 `status` 改成 `hidden`，刷新页面后它就不会显示；也可以在这里删除评论。
- `comment_identities`：访客昵称登记表。一行一个浏览器：`author_key` 是哈希后的浏览器标识，`display_name` 是分配的唯一昵称。删除某行只会让该访客下次评论时重新领名，不影响已有评论的显示（评论上有名字快照）。
- `comment_rate_events`：成功评论的限流记录。一条成功评论对应两行，分别给浏览器和 IP 计数；`comment_id` 指向相应的评论，`subject_key` 是带服务端密钥的散列值，不能直接看出原始 IP。
- `comment_rate_subjects`：并发提交时使用的计数锁。它不含评论内容。

评论按笔记的 `slug` 关联。若以后重命名或移动笔记，旧评论仍在数据库中，但不会自动出现在新地址下；可以在 phpMyAdmin 中把对应行的 `note_slug` 更新为新值。

例如在 phpMyAdmin 的 SQL 页签查看最近的评论：

```sql
SELECT id, note_slug, content, status, created_at
FROM website_comments.comments
ORDER BY id DESC
LIMIT 50;
```

服务会在约每 20 条成功评论后尝试清理过期的限流记录。长时间没有新评论时，旧记录会等下次成功评论再清理；它们不会再参与限流。正式服务器可另外设置每天一次的宝塔计划任务，执行：

```sql
DELETE FROM website_comments.comment_rate_events WHERE created_at <= UTC_TIMESTAMP(6) - INTERVAL 24 HOUR;
DELETE FROM website_comments.comment_rate_subjects WHERE last_seen <= UTC_TIMESTAMP(6) - INTERVAL 2 DAY;
```

要看被拒绝的请求和服务器故障，请使用宝塔「网站 → 日志」查看该站点的 Nginx 访问日志和错误日志；访问日志中的 `429` 是限流拒绝。PHP 的异常会写入服务器配置的 PHP 错误日志。数据库只保存成功评论的限流事件，不会给每一次被拒绝的请求另建一行，以免攻击时日志表被刷满。Nginx 访问日志通常会记录原始访客 IP，应按需要设置日志保留时间。
